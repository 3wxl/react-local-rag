# 双端对比报告（M1）

> 生成时间：2026-10-12　|　生成脚本：`apps/api/scripts/compare_ends.py`　|　数据：`packages/eval/baseline/bench-{ts,python}.json`

对比口径：**同一份 golden（61 条：25 技术措辞 / 14 口语化 / 12 单文档多主题 / 10 负样本）、同一份固化向量（`packages/eval/embeddings.json`）、同一套默认参数**。两端都只跑检索管线（BM25 + 余弦 + RRF + 邻近合并 + 去重 + MMR + 门限），**不含模型加载**——模型加载与首次可用时间单列在本报告第 6 节。

## 0. 一句话结论

- **召回一致性 100%**：61 条查询里，两端 top-3 覆盖的 relevant 原句集合与 top-1 文档**完全一致**。这不是「差不多」，而是跨语言同口径的直接证据（详见第 1 节）。
- **延迟**：浏览器端（Node 等价路径）p50 1.149ms / p95 2.09ms；服务端 p50 25.52ms / p95 34.468ms —— 端侧快约 **22.2×**，因为同一套算法在 V8 的 TypedArray 上是原生循环，在 Python 里是解释执行。
- **内存**：浏览器端进程 RSS 峰值 95.1MB，服务端 49.0MB（含解释器与运行库；浏览器真正的约束是 WASM 堆与约 1GB 的页面预算，见第 4 节）。
- **结论**：小语料（≤ 数百块）/ 数据不出域 / 断网可用 → 浏览器端；语料大、需要 ACL 与审计、要并发出多用户 → 服务端。判定依据见第 7 节。

## 2. 延迟（检索阶段，毫秒）

| 实现 | p50 | p95 | mean | max | 相对倍数（p50） |
| --- | --- | --- | --- | --- | --- |
| 浏览器端（TS，Node 等价路径） | 1.149 | 2.09 | 1.318 | 4.074 | 1.0× |
| 服务端（Python） | 25.52 | 34.468 | 26.403 | 41.46 | 22.2× |

读法：两端做的是同一件事（同输入、同参数、同算法），差异来自**语言与运行时**，不是实现分歧。服务端的这个量级在 119 块语料上无感；语料上万块时需要做的是「SQL 里的向量 topN 下推 + BM25 倒排表」（pgvector HNSW / pg_trgm 已建好索引），而不是把 Python 循环优化成 C —— 见第 7 节的扩展路线。

## 3. 单次成本

| 实现 | 检索 | 生成（本地模型） | 说明 |
| --- | --- | --- | --- |
| 浏览器端 | 0 | 0 | 本地推理，无 API 计费；成本是用户的设备与电量 |
| 服务端（本地 ONNX） | 0 | 0 | 同上，账单为 0；成本是服务器折旧与电费 |
| 服务端（云端通道，可选） | 0 | 按 token 计价 | `LLM_PROVIDER=ollama` 之外的云端通道会写进 `cost.tokens` 与 `evidence_snapshot.model`，便于按请求归因 |

成本口径的可信度来自**可归因**：每个回答都带 `cost.latency_breakdown_ms` 与 `cost.tokens`，且 `evidence_snapshot` 冻结了当时的模型与参数（M6 的 OTel 归因以此为起点）。

## 4. 内存与资源占用

| 实现 | 进程 RSS 峰值 | 运行时资源约束 |
| --- | --- | --- |
| 浏览器端 | 95.1MB（Node 等价路径） | 页面内 WASM 堆 + 主线程：模型常驻约 400MB（Qwen2.5-0.5B q4）、BGE 约 100MB、精排开启再加 300~400MB；**单线程推理锁**串行化所有请求 |
| 服务端 | 49.0MB（Python + numpy，不含模型） | 进程内模型常驻，可多请求并发（ONNX Runtime 内部线程池）；内存随语料增长（块 + 向量 ≈ 119 块 / 0.6MB，按线性外推） |

注意：这里的内存数字**不含模型加载**（两端都不加载模型）。浏览器端的真实约束不是 RSS，而是页面预算（约 1GB）与 COOP/COEP 下的 SharedArrayBuffer 可用性 ——这也是 Lite 模式把精排默认关掉的原因（见 `useAgentSettings.ts` 的默认值注释）。

## 5. 离线可用性

| 场景 | 浏览器端 | 服务端 |
| --- | --- | --- |
| 完全断网 | ✅ 可用（模型与语料都在本地） | ✅ 可用（同机部署时） |
| 数据不出域 | ✅ 数据不出浏览器 | ✅ 可保证（自托管，无外呼） |
| 跨设备/多人共享同一索引 | ❌ 每个浏览器各存一份 | ✅ 单库共享 |
| 审计（谁在什么时候问了什么） | ❌ 无服务端记录 | ✅ answers/traces 落库，trace 自包含可回放 |
| 权限/密级过滤（ACL） | ❌ 没有身份概念 | ✅ filters 在召回层生效（M2 接 ACL） |

## 6. 模型加载与首次可用（单项实测）

| 阶段 | 浏览器端 | 服务端 |
| --- | --- | --- |
| 嵌入模型加载 | WASM q8，首次约数秒（随构建产物离线分发） | ONNX q8，实测约 6.4s 冷启动 / 首次编码 0.9s（进程内常驻） |
| 生成模型加载 | Qwen2.5-0.5B q4 约 400MB，首次十秒级 | ONNX q4，实测约 6.4s（同文件、CPU EP） |
| 首次查询端到端 | 检索 + 生成都在页面内（约秒级，取决于设备） | 本机 0.5B 贪心 64 token：实测约 8.1s（含加载） |

两端的嵌入向量由**同一份 ONNX 权重**产生，但运行时不同（onnxruntime-web WASM vs onnxruntime CPU），实测余弦一致度：文档块 0.998、查询 0.993 —— 属运行时数值差异，不改变检索结果（第 1 节的一致性已证明）。

结论：**两端在答案质量上是同一个水平线**（同模型同 Prompt），当前短板一致 —— 弱模型不产角标、只答部分要点。这正是 M2「可靠性与弱模型工程」要解决的问题（引用强制闭环 + 拒答裁决），不是双端实现差异。

## 7. 结论：什么场景该用哪端

**用浏览器端（Lite 模式）**：

- 数据不能出本机 / 不能出浏览器，且**没有人愿意为服务器买单**的场景
- 语料规模在**数百块以内**（本评测 119 块；再大时页面内存与单线程推理锁会先撑不住）
- 单用户、单设备，不需要共享索引，也不需要审计

**用服务端**：

- 语料规模上千块、要多人共享同一份索引，或需要索引**增量重建与灰度**
- 需要「谁问过什么、答案依据是什么」可审计可回放（`/v1/answer/{id}/trace`）
- 需要按部门/密级做**召回层过滤**，或需要接更大的模型（7B/14B 在浏览器里不现实）

**当前分界线**（本报告实测）：检索阶段两端召回完全一致、延迟差一个数量级但绝对值都在毫秒级；真正的分界不在性能，而在**多用户共享、审计、权限与模型规模**这四件事 —— 它们浏览器端做不了，服务端才有。反过来说，只要这四件事都不需要，浏览器端就是更省事、更合规的选择。
