# 检索评测基线

## 一条命令

```bash
npm run eval:all        # 三块指标一次跑完（检索 / 校验 P/R / 答案级）
```

拆开跑：

```bash
npm run eval                     # 检索指标，存档到 results/
npm run eval:verify -- --check   # 幻觉校验组件 P/R（读固化打分，无模型）
npm run eval:answers             # 答案级评测（需本地 Qwen，61 条查询约 15 分钟）
npx tsx scripts/eval.ts --topk 5 # 自定义要点命中统计的 topK
```

三者回答的是不同问题，缺一不可：

| 命令 | 回答的问题 | 需要模型 | 进 CI |
| --- | --- | --- | --- |
| `eval` | 相关片段**被检索到**了吗 | 否（读固化向量/精排分） | ✅ |
| `eval:verify` | 生成的句子**有原文依据**吗 | 否（读固化打分） | ✅ |
| `eval:answers` | 要点**真的写进答案**了吗 | 是（本地 Qwen） | ❌（本地跑） |

结果存档在 `results/<时间戳>.json`，`results/latest.json` 恒指向最近一次。
CI 中跑 `npm run eval`，指标低于门槛直接红。

**存档保留策略**：`results/` 整个目录已 gitignore（不进仓库），本地只保留
`latest.json` + 最近 20 个存档，更早的在每次跑 eval 时自动清理 —— 否则每跑一次就多一份，无限增长。

## 数据在哪

**全部在 [public/eval/](../../public/eval/)**（放在 `public/` 是为了浏览器开发者工具能 fetch 到同一份，
不允许出现「Node 一份、浏览器一份」的副本）：

| 文件 | 内容 |
| --- | --- |
| `corpus/*.md` | 语料：5 篇手写目标文档 + 4 篇 3000+ 字手写长文档（15-16 块/篇，测跨块窗口）+ 40 篇干扰文档（10 篇同族近义 + 30 篇异题），默认 256 token 切块共 119 个块 |
| `golden.json` | 61 条 golden QA（25 条技术措辞 q + 14 条口语化改写 s + 12 条单文档多主题 m）+ 10 条负样本。命中判定三类统一：top-k 窗口文本包含 `relevant` 原句即命中，不维护 contentHash |
| `embeddings.json` | **离线固化向量**（可选，见下）。存在则评测跑混合检索，缺则退化为纯 BM25 |
| `verify-labels.json` | 幻觉校验阈值校准的人工标注集：**5 篇文档 / 72 句**（有依据 42 / 无依据 30） |
| `verify-scores.json` | 上述标注集的**固化打分**（`calibrate-verify.ts` 生成一次、提交；CI 的 `--check` 读它复算 P/R，无需模型） |

`scripts/eval.ts` 等脚本都用 `readdirSync` 直接读盘，新增手写语料文件无需刷新任何清单；
只有批量生成干扰文档时才需要跑 `node scripts/gen-corpus.mjs`。

## 语料怎么构造（踩过的坑）

干扰文档分两类，比例是关键：

| 类型 | 数量 | 作用 |
| --- | --- | --- |
| 同族近义 | 每族 2 篇（共 10） | 最难的一类：同模板、只换数字，测"能否把正确的那篇排前面" |
| 异题 | 30 篇（`topic-corpus.mjs`） | 语料体量来源：主题/术语/句式都不同，只在通用词上重叠 |

**坑：同族近义文档一多，整个评测就废了。** 曾经生成 68 篇同模板文档
（产品手册 18 篇、员工手册 14 篇……），后果是：

- 任何查询（**包括负样本**）都能在库里找到余弦 0.45+ 的块，相似度"地板"被抬高
- 实测正样本最大余弦 0.560~0.649 / 口语化 0.501~0.631 / 负样本 0.459~0.569，
  **三组互相重叠**，所有拒答信号集体失效
- 向量路文档级 top1 只有 36%：干扰手册余弦 0.595 反超真手册 0.591，
  句向量分辨不出数字差异，而 BM25 恰好擅长匹配数字

真实语料里问「标准版售价」通常只有一两篇文档能答上来。
所以同族近义**每种只留 2 篇**，其余体量交给异题文档。

## 门槛取值纪律

**连续型指标用「实测 − 固定余量」，二值/计数型指标用绝对条数。**

| 类型 | 例子 | 为什么 |
| --- | --- | --- |
| 连续型 | 分组 recall@3（实测 0.92 / 0.29 / 1.00 → 门槛 0.85 / 0.20 / 0.90） | 留余量平滑波动，避免个别样本抖动误报 |
| 计数型 | **负样本拒答条数 ≥ 3/10**（实测 4/10） | 比率门槛等于实测值（如 = 0.4）：10 条样本翻转 1 条就掉 10pt，随机变红却不反映真实退化 |
| 二值型 | 误拒数 = 0、精排变化率 > 0、近似重复率 = 0 | 含义明确，不需要余量 |

每条门槛都在 `scripts/eval.ts` 里带注释：取值、依据、设定日期。

## 指标

2026-10-03 实测（119 块，51 正 + 10 负，hybrid）：

- recall@3 = 0.76、recall@5 = 0.82、要点命中率 = 0.88、负样本拒答 = 0.40、误拒 = 0（精排列另见下一节）
- **分组**：技术措辞 0.92、口语化 0.29、单文档多主题 1.00

门槛：分组 recall@3（q ≥ 0.85、s ≥ 0.2、m ≥ 0.90）、各组误拒 = 0、负样本拒答 ≥ 0.40、
top3 近似重复率 = 0、精排 top-1 变化率 > 0。

| 指标 | 含义 | 门槛 |
| --- | --- | --- |
| **q 组 recall@3** | 技术措辞正样本（25 条）的命中比例 | **≥ 0.85** |
| **s 组 recall@3** | 口语化正样本（14 条）的命中比例 | **≥ 0.20** |
| **m 组 recall@3** | 单文档多主题正样本（12 条）的命中比例 | **≥ 0.90** |
| **误拒数** | 任一组正样本被拒答的条数 | **必须 = 0（每组）** |
| **负样本拒答条数** | 「文档未提及」的问题被正确拒答的**条数** | **≥ 3/10**（实测 4/10） |
| **top3 近似重复率** | top-3 内两段文本 bigram Jaccard ≥ 0.8 | **必须 = 0** |
| **精排 top-1 变化率** | 精排改变排序的比例（防静默失效） | **必须 > 0** |
| **精排 recall@3** | 开精排后的 recall@3 | **≥ 无精排 − 0.01**（精排不能帮倒忙） |
| **精排缺分对数** | 候选查不到固化精排分的对数 | **必须 = 0** |

### 冗余指标为什么用「内容口径」而不是「ord 相邻」

两个口径都在算，但**只有内容口径设门槛**：

```
结构性（ord 相邻/重叠）: 0.1765   ← 9 条查询出现，但明细显示 Jaccard 仅 0.107~0.157
内容性（Jaccard ≥ 0.8）: 0.0000   ← 实测为 0，门槛也设 0
```

存档里带 `dupDetail`（两侧 ord 区间 + Jaccard）。实测那 9 条是
`ordRanges=[[12,15],[8,11]]` 这类**长文档里首尾相接的两个窗口**，
内容 Jaccard 只有 0.1 上下 —— 它们各自回答问题的不同部分，不是用户可感的重复。

所以：结构口径留作诊断，内容口径用来设门槛。
若哪天内容口径出现非零值（两段文本真的几乎一样），那才是 `mergeNeighbors` 要修的信号。

无向量路时召回类与拒答类门槛都不设固定阈值（只有完整口径才有意义），
但**分组门槛仍然生效**。

门槛数值取自实测基线往下留余量，作用是**防回归**，不是定目标。

**拒答两条件必须成对设**：只压 `negativeRefusedCount` 会把系统调成哑巴
（全部拒答时它会到顶），只压 `falseRefusalCount` 则等于不拒答。
两个一起才是「该拒的拒、不该拒的不拒」。

## 拒答：区分"调参口径"与"保守口径"

`npm run tune:retrieval` 第 7 段做**信号可用性诊断**，判据是
「**零误拒**前提下能拒掉多少负样本」。这里有个关键区分：

- **调参口径**：正样本只算 q（关键词）+ m（多主题），**不含** s（口语化语义难例）。
  用于**选参数**。
- **保守口径**：把 14 条 s 也纳入保护。用于**观察难例代价**。

2026-10-03 实测（119 块语料，51 正 / 10 负）：

| 信号 | 调参口径（q+m） | 保守口径（含 s） |
| --- | --- | --- |
| IDF 覆盖率 | 60.0% 门限 0.199 ✅ | **0.0%** ❌（会误伤 12/14 条 s） |
| BM25 最高分 | 80.0% 门限 7.794 ✅ | **0.0%** ❌ |
| 最高余弦 | 50.0% 门限 0.504 ❌ | 50.0% ❌ |
| 余弦对比度 | 10.0% ❌ | 10.0% ❌ |
| 精排最高分 | 60.0% 门限 0.014 ✅ | **0.0%** ❌（最优 F1 时误拒 6 条） |

**两个口径结论分叉时，以调参口径选参，s 难例的「文档未提及」交给答案侧证据校验**
（`verifyAnswer` 的语义 + 词法 + 数字核查）。这正是当前的设计：
**检索侧弱门限放行，答案侧细拒**。

### 为什么精排不做绝对分拒答

精排分在调参口径下可用（60%），但**加进口语化难例后降到 0%**：
bge-reranker-base 的 logit 对「跨查询的全局置信度」不可靠 ——
正样本里存在 -10 量级的离群值，与负样本分布重叠，任何绝对门限都会误拒。
所以精排只做**相对排序**，不参与拒答判定（`DEFAULT_RETRIEVAL_OPTIONS` 里没有 `minRerankScore`）。

其余信号不可用的原因：

- **IDF 覆盖率**抓的是"词表覆盖"，不是"主题存在"。口语化查询
  （"严寒酷暑下还能正常干活吗"）问的正是语料里有的温度指标，
  但用词与语料完全不同，覆盖率同样很低，与负样本无法区分。
- **对比度 / BM25 最高分**同理：低动态范围模型下不相关文本的得分也有 0.45~0.5。

## 精排进评测：两列并存 + 保活门槛

`public/eval/rerank-scores.json` 是精排分的**固化产物**（`npm run gen:rerank` 生成），
与 `embeddings.json` 同一套思路：构建机用真实模型算一次，评测端确定性复现。
`eval` 因此能稳定输出两列：

```
主   列（线上默认口径，精排关闭）: recall@3=0.765  recall@5=0.824  MRR=0.678  要点=0.877
精排列（可选配置）              : recall@3=0.804  recall@5=0.804  MRR=0.699  要点=0.852
top-1 变化率                    : 0.4314   （43% 的查询 top-1 被精排改变）
```

### 精排对哪一类查询有效（分组数据）

```
技术措辞     n=25  0.9200 → 0.9600   (+4.0pt)
口语化       n=14  0.2857 → 0.4286   (+14.3pt)   ← 增益最大
单文档多主题 n=12  1.0000 → 0.9167   (-8.3pt)    ← 反而退化
```

两条结论：

1. **精排的最大增益正好落在最需要救的口语化组（+14.3pt）** —— 因为交叉编码器
   直接建模 (query, passage) 相关性，不依赖二者共享词汇，这正是纯向量/BM25 的短板。
   但 **0.4286 仍低于 0.5 的目标**，说明精排是必要不充分的：口语化要达标还得上
   查询扩展（本地 0.5B 生成术语化改写 + 多查询 RRF）或 HyDE。
2. **m 组退化 -8.3pt 是结构性的**：m 组的标注要点跨同一文档的多个窗口，
   答案需要"覆盖多个窗口"；而精排按单条 passage 的相关性打分，
   会把分数最高的那个窗口顶上来、把第二个相关窗口挤出去。
   **精排优化的是单片段相关性，m 组要的是覆盖率，两者目标不同。**

### 线上默认口径 = 精排关闭

**主列就是用户实际拿到的效果**。精排是**可选配置**（设置面板手动开），
因为它的代价是实测出来的：

| 维度 | 代价 |
| --- | --- |
| 内存 | +300~400MB（模型 q8 常驻，与 BGE + Qwen 同时驻留会触发 `std::bad_alloc`，故有「生成前释放精排」机制） |
| 延迟 | 单次查询 +1.7s（10 条候选批量精排，Node 单线程实测，浏览器 WASM 同量级） |
| 收益 | recall@3 +3.9pt（0.765 → 0.804） |

收益为正但代价是可感量级，因此不进默认路径。eval 输出里显式标注了这一行 ——
**两列混着看会高估线上效果**，这是之前踩过的坑。

### 两条防失效设计

1. **量纲对齐**：固化文件存**原始 logit**，加载时转 sigmoid 成线上口径
   （worker 走 `text-classification` pipeline，config 声明了
   `problem_type: multi_label_classification`，输出是 sigmoid 后的 (0,1) 分）。
   两者单调等价、排序一致，但阈值量纲不同 —— 不转换就会让诊断扫出的门限完全失效。
2. **两条互不替代的断言**：
   - `top1ChangedRate > 0` 且 `missingPairs = 0` —— 防**静默失效**。
     曾经 config 缺 `problem_type`，单 logit 走 softmax 恒为 1，全体候选同分、
     排序原样不动，但链路"跑通了"、指标也没崩，只有变化率能发现。
   - `rerank.recall@3 ≥ 无精排 − 0.01` —— 防**帮倒忙**。变化率只证明"动了"，
     不证明"动对了"：把固化 logit 取反验证过，变化率反而升到 **0.96**（看起来更活跃），
     而 recall@3 从 0.804 崩到 **0.137**。两条断言缺一不可。

参数窗口依赖（`maxWindowChars` / `windowRadius`）不影响固化产物：
固化分按**块**算，窗口分取块内最高分聚合，所以改窗口参数不必重算 7000 多对精排分。

### 一条必须遵守的搭配：向量可用时不给 BM25 豁免

`bm25ExemptRank`（BM25 排前三即豁免门限）**只在向量降级时生效**。
实测豁免一旦在向量可用时生效，负样本靠「公司」「产品」这类通用词的 bigram
命中就能排进 BM25 前三，**端到端拒答率从 60% 掉到 0%**。
两者是互斥的判据，不能叠加。

## 参数扫描：`npm run tune:retrieval`

把「拍脑袋的默认值」换成有曲线支撑的选择。共七段，每段给出一条曲线：

| 段 | 参数 | 影响 | 看什么 |
| --- | --- | --- | --- |
| 1 | `maxChunkTokens` | 分块（每换一个值都重新切块建索引） | **文档级 top-1**（见下方警告）、块数 |
| 2 | `rrfK` / `vecWeight` / `bm25Weight` | RRF 融合权重 | hybrid vs BM25-only 的**相对门槛**（见下） |
| 3 | `minVecScore` | 相关度门限 | **P/R 曲线**（正样本该命中 / 负样本该拒答的二分类） |
| 4 | `mmrLambda` | MMR 多样性权重 | recall@3 与冗余占位率 |
| 5 | `minIdfCoverage` | 拒答信号 1 | 覆盖率两类分布（**结论：该信号不可用**） |
| 6 | 精排（开关） | 重排增益 | RRF 顺序 vs logit 重排指标 |
| 7 | 拒答信号可用性诊断 | — | 每个信号在**零误拒**前提下的拒答率 |

第 7 段「拒答信号可用性诊断」是决定能不能设拒答门槛的前置测量，
输出每个信号在**零误拒**前提下的拒答率；两口径对比与结论见
「[拒答：区分"调参口径"与"保守口径"](#拒答区分调参口径与保守口径)」。

> ⚠️ **句级 recall 对块大小天生有偏**：块越大，一个窗口越可能顺带盖住关键句，
> 「recall 上升」未必是检索变准了。所以扫描脚本额外输出**文档级 top-1**
> （top-1 是否来自包含答案的那篇文档），它与块大小无关，只有它能判断
> 「是不是真的把对的文档排到了第一」。

### maxChunkTokens：256 的决策依据

`maxChunkTokens` 默认值为 **256**（[chunk.ts](../../src/utils/chunk.ts)）。

2026-10-03 扫描，**所有行同口径**（tune 第 1 段的 `liveEmbeddings` 模式：对每个候选块大小
在线实时编码，因此每行都是真实的 hybrid 指标，可以横向比较）：

```
maxChunkTokens  块数   文档top1  recall@3   MRR      模式
      128       384     59.5%     86.5%   73.8%   hybrid
      160       242     54.1%     89.2%   70.8%   hybrid
      200       164     67.6%     94.6%   80.3%   hybrid
      256       119     70.3%     94.6%   82.2%   hybrid   ← 默认值（两项均为最优）
      320        94     67.6%     94.6%   80.6%   hybrid
      384        80     67.6%     94.6%   80.9%   hybrid
      448        74     62.2%     94.6%   78.6%   hybrid
```

判据是**文档级 top-1**（top-1 是否来自含答案的那篇文档）：它与块大小无关，
而句级 recall 对块大小天生有偏（块越大越容易顺带盖住关键句）。
256 在文档级 top-1 与 MRR 上同时最优。

> 早先这张表曾出现「384 是默认、其余行是纯 BM25」的**跨模式比较**，结论不可用。
> tune 第 1 段现在默认走 `liveEmbeddings`，从根上避免了这个问题；
> 若因故退回固化向量模式，脚本会显式标注每行的模式并拒绝跨模式下结论。

> ⚠️ **改这个值会让用户侧索引重建。** `DEFAULT_CHUNK_OPTIONS` 参与
> `CURRENT_INDEX_VERSION` 的 hash，改动后现有索引被判定过期，
> UI 会提示「索引已过期，请重新上传文档」，用户需重新上传文档才能检索。
> 调整前先跑 tune 第 1 段确认新值确实更优，并把这个成本写进发布说明。

### RRF 权重 × k：扫描过，维持 1/1 + k=60

`rrfK = 60` / `vecWeight = 1` / `bm25Weight = 1`（三个值都在
[retrieval.ts](../../src/utils/retrieval.ts) 的 `DEFAULT_RETRIEVAL_OPTIONS` 上带注释）。

2026-10-03 扫描（tune 第 2 段，119 块语料，hybrid 同口径全实时编码）：

- `vecWeight` ∈ {0.5, 1.0, 1.5, 2.0} × `k` ∈ {20, 40, 60, 80} 共 16 组，
  文档级 top-1 / recall@3 / MRR **全部完全相同** —— 本语料上两路排名高度一致，
  相对权重几乎不影响 top-3。
- 可用性自检：把 `vecWeight` 拉到 100，MRR 也只动 0.0005（0.6781 → 0.6776），
  证明参数确实作用在排序上，只是**没有任何一组显著优于默认值**。
- 既然无一组更优，就不偏离论文默认（Cormack et al. 2009：等权 + k=60）；
  改成别的值等于凭空引入无依据的超参。待语料分散度提高后重扫。

扫参时 `bm25Weight` 固定为 1（只扫两路相对权重比）—— 融合分对整体缩放的
排序等价性决定了两路权重只有比值有意义。

**相对门槛已搬进 CI**（[eval.ts](../../scripts/eval.ts)）：
`hybrid recall@3 ≥ BM25-only recall@3 × 0.95`。它不依赖语料难度，专门兜住
「融合配置退化」—— 两路权重调歪、向量路被错误压制、RRF 实现改坏，
这类问题不会击穿绝对门槛，但会让向量路白开。

### minVecScore 与 mmrLambda：曲线已补齐，但当前语料无法支持改动

有了 `embeddings.json` 后两条曲线已可扫（2026-10-01 实测）：

- `minVecScore` 在 0.20 ~ 0.55 之间指标**完全相同**（precision 71.4%、recall 100%、F1 83.3%、
  负样本拒答率 0）—— 注意这是 **2026-10-01 旧语料（45 块）**上的曲线，当时干扰文档的余弦
  与正确文档一样落在门限之上，门限不起作用。**现行默认值是 0.5、不是 0.35**
  （[retrieval.ts](../../src/utils/retrieval.ts)，2026-10-02 改）：取「q + s 两类人群都零误拒」
  的最宽点。当前 119 块语料上 eval 实测 0.5 → 负样本拒答 4/10、正样本零误拒，
  该点即拒答门槛（≥ 3/10）的依据；**扩语料后完整曲线仍待重扫**（tune 第 3 段）。
- `mmrLambda` 在 0.5 ~ 0.9 指标完全一致（recall@3 = 48%、冗余率全程 0），
  **λ = 1.0（关闭 MMR）反而更高**（recall@3 = 60%、MRR = 57.2%）——当前语料上 MMR 牺牲了相关性
  却没换来多样性收益。但这与上面的语料偏差同源，默认 0.7 暂不动，待语料分散后重扫确认。

### 负样本拒答：纯 BM25 不设门槛，hybrid 设「绝对条数」门槛

纯 BM25 只要命中一个词项就给分，它没有「语义上根本不相关」这个概念，拒答率为 0 属预期，
因此**无向量路时不判失败**。hybrid（向量可用）下余弦门限能粗滤掉一部分负样本：
当前 119 块语料实测拒掉 4/10，门槛按「实测留 1 条余量」设为 **≥ 3/10**
（为什么用条数而不是比率，见「门槛取值纪律」）。
分不开的负样本不靠提高门限硬拒 —— 那会误伤口语化正样本 —— 放行给答案侧
`verifyAnswer` 做最终置信度裁决。

## 向量路（离线固化）

CI 里没有模型（`public/models/` 是 gitignore 的，且上百 MB），向量路长期不在评测范围内 ——
混合检索与精排的回归完全没有保护，曾经的问题就藏在这个盲区里。

做法：在**有模型的机器**上把语料块与查询各算一次向量，存成 `embeddings.json` 提交。
评测时直接读这份向量算余弦，结果确定、可复现、无需模型。

生成步骤（在有模型的机器上跑，需要能正常运行的 onnxruntime-node，见下方「原生运行时」）：

```bash
npm run gen:embeddings
# 产物直接写入 public/eval/embeddings.json
```

生成后跑 `npm run eval`，模式应变成 hybrid（向量+BM25）。

**语料或分块参数一变，向量必须重新生成。** 这一点由 `assertEmbeddingsConsistent`
硬性拦截：模型标识、分块参数、块的 contentHash、查询 id 四项任一不一致就直接报错退出，
不允许拿旧向量跑出一个假的指标。

### Node 版本要求：≥ 22

`package.json` 里声明了 `engines.node: ">=22"`。**Node 20 会直接跑不起来**：
vitest 5 / jsdom 的依赖链里有 ESM-only 包，被 CJS `require()`，
而 `require(esm)` 要到 Node 22 才默认可用 —— 在 Node 20 上会报
`ERR_REQUIRE_ESM: require() of ES Module ... not supported`。

### 原生运行时（Node 路径的前提）

`npm run gen:embeddings` 依赖 `onnxruntime-node` 的原生二进制。若它在本机不可用，
会以两种方式失败：`ERR_DLOPEN_FAILED`（加载不了 .node）或**加载成功但建 session 时段错误**。
这不是本项目的代码或模型问题 —— 用最小复现可以确认：

```js
import ort from "onnxruntime-node";
await ort.InferenceSession.create("public/models/Xenova/bge-small-zh-v1.5/onnx/model_quantized.onnx");
// 在本机直接段错误（exit 139），与 transformers.js、模型文件都无关
```

Windows 上常见原因是缺少 **Visual C++ 可再发行组件**（MSVC runtime），
或原生包解压不完整。处理顺序：装 VC++ Redistributable x64 → `rm -rf node_modules && npm ci`
→ 仍不行则需先修复本机原生运行时，没有其他等价生成路径。

另注：不要在项目里另外装一个顶层 `onnxruntime-node`。transformers.js 自带对应版本
（写在它自己的 dependencies 里），顶层再装一个不同版本会造成原生模块混用。

## 幻觉校验组件的 P/R

校验是「检索侧粗拒」之后的第二道拒答防线。它的能力现在有量化：

```bash
npm run eval:verify            # 需本地模型：算分 + 写固化产物 + 出报告
npm run eval:verify -- --check # 无模型：读固化打分复算 P/R（CI 用这个）
```

**实测（5 篇文档 / 72 条句子，有依据 42 / 无依据 30，2026-10-03）**：

```
precision = 75.0%   recall = 100.0%   F1 = 85.7%
幻觉漏放(FP) = 14   误伤(FN) = 0
```

读法：**有依据的句子一条都没误伤**（recall 100%，用户不会看到"正常句子被标红"），
但 30 条捏造句里放过了 14 条。

为什么 precision 上不去：标注集里的"无依据"多是**同一句话改个数字**
（「售价 4980 元」vs 原文「3980 元」）。语义分分布**几乎完全重叠** ——
有依据均值 0.622（最低 0.476）/ 无依据均值 0.568（最高 0.733）。
bge-small-zh 分辨不出数字差异，只有数字核查能抓，而数字核查只覆盖"数字完全不同"的情形。

**这是模型的固有上限，不是实现问题。** 门槛因此按实测留余量设：
precision ≥ 0.7 / recall ≥ 0.9 / F1 ≥ 0.75（`recall` 门槛高，因为误伤对用户直接可感）。

### 两条工程细节

1. **固化打分**：CI 没有模型（`public/models` 是 gitignore 的），
   所以 `--check` 读 `verify-scores.json`（有模型的机器生成一次、提交），
   只做纯函数的阈值判定。打分函数 `computeSentenceScore` 两边共用，口径不会漂移。
   改标注集后必须重新生成，否则 `--check` 会因 id 对不上直接报错。
2. **数字核查必须共用同一个函数**：`findUnknownNumbers` 有两个易错点 ——
   要去掉单位再比核（`"15天"` 的核是 `"15"`），且要比对数字边界（否则 `"100"` 命中 `"1000"`）。
   校准脚本最初自己写了一遍，漏了第一条，凭空多出 6 条"误伤"。
   抽成导出函数后两边共用，不可能再错。

## 答案级评测：要点真的写进答案了吗

检索指标只证明「相关片段被召回」，校验 P/R 只证明「生成的句子有依据」；
两者都不回答**该写的要点有没有写进答案**。`eval:answers` 跑真实本地 Qwen 走完整链路
（同一套 `postProcessRetrieval` + 同一个 `buildAnswerPrompt`），统计要点原文在答案中
出现的比例：

```bash
npm run eval:answers   # 需本地 Qwen，61 条查询约 15 分钟
```

**实测（2026-10-03，51 正 / 10 负，Qwen2.5-0.5B-Instruct q4）**：

```
要点命中率：检索口径 0.877  →  答案口径 0.42
答案带引用角标比例 = 0.0
负样本拒答率 = 0.4（口径 = 检索门限滤空或模型自述"没有找到"）
```

读法：**检索不是瓶颈，0.5B 生成才是。** 要点进了上下文，模型仍会漏写、
改写错数字（「500 元」写成「591 元」、「2 个月工资」写成「1.9 个月」）、
甚至整句编造（q014 整段数字全错）。检索口径 0.877 与答案口径 0.42 之间的差距
就是生成损耗 —— 这个差距在只看检索指标时完全不可见。

两个口径细节：

- **匹配前双方都去掉空白**：golden 的要点按可读性写成「3980 元」，而模型输出是
  「3980元」。直接 `includes` 会把纯格式差异误判成漏答 —— 不去空白实测 18.5%、
  去空白 42.0%，差出来的全部是同一个空格。
- **引用角标 0.0%**：0.5B 模型不遵守「逐句标注 `[n]`」的指令。这不影响校验收敛的
  正确性（`verifyAnswer` 找不到角标时按全部候选校验），但 UI 的引用卡片与
  校验范围收敛都依赖角标 —— 要引用可点，需要更大的模型或后处理补挂。

逐条明细写在 `public/eval/answer-eval.json`（该文件是本地产物，已 gitignore）。

## 为什么评测脚本直接 import src

旧版 `scripts/eval.mjs` 手抄了 tokenize / BM25 / 分块 / RRF，注释写着「与 src/utils 同口径的移植」。
那和「两份 tokenize 靠注释同步」是同一类风险，而且抄的是更复杂的逻辑，漂移概率更高。

现在 `scripts/eval.ts` 直接 import `src/utils/{bm25,chunk,retrieval}`：
**评测跑的就是线上跑的那份代码**，口径不可能分叉。
[src/utils/evalImports.test.ts](../../src/utils/evalImports.test.ts) 守这条线 ——
一旦有人在脚本里重新内联这些算法，测试会失败。

## 扩充语料

- 手写目标文档：直接往 `public/eval/corpus/` 加 `.md`
- 批量干扰文档：改 `scripts/gen-corpus.mjs` 里的名称列表与事实表，然后 `node scripts/gen-corpus.mjs`

干扰文档的关键是**同族**：同样的文档类型、同样的句式，只是事实不同。
这样一条「标准版售价多少」会同时命中目标文档和十几篇同类手册，检索必须真的排对。
用无关领域文本填充的话，靠停用词就能分开，等于没测。
